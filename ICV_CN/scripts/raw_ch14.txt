     This chapter explains the DRC waivers capabilities of the IC Validator tool and how to use
     this feature.

     The DRC waivers capabilities are described in the following sections:
      • Defining Waivers
      • Creating a Waiver Database
      • Using a Waiver Database
     DRC waivers allow you to classify and annotate errors found during an IC Validator run
     and export the errors into a waiver database for use in subsequent IC Validator runs. The
     DRC Waivers flow is separated into three distinct steps:
      • Defining which errors might be waived, and annotating the error database through VUE
        or the icv_pydb command-line utility
      • Creating a persistent waiver database on disk
      • Applying the waivers to subsequent IC Validator runs
     Each of these steps is described in the following sections.

Defining Waivers
     You can review design errors written to the error database (PYDB) using VUE or the ASCII
     Error Report file, cell. LAYOUT_ERRORS. In many designs, there are DRC violations
     that can be waived, that is, these errors do not need to be fixed in the layout. This could
     be a temporary waiver that must be fixed before the design is taped out, or a permanent
     waiver that is approved by the foundry. You can add a user comment or predetermined
     waiver properties to waivers to give more context to other engineers that are reviewing the
     waivers.




     The IC Validator SQLite error database allows for concurrent access by multiple users; as
     errors are reviewed and waivers are applied, other users who access the database can
     see the updates you have applied.
     IC Validator supports several waiver classes:
      • Persistent waiver classes: Waive, Watch, Ignore
      • Non-Persistent waiver classes: Error, Fixed
     Persistent waiver classes can be exported to a waiver database. See Creating a Waiver
     Database. With multiple persistent waiver classes, you can segregate waived errors into
     different categories. This makes waiver management easier during the design process.
     Each of these waiver classes are treated equally. For example, you can choose Waive
     when the error will be waived throughout the design process all the way to tapeout, and
     choose Watch to designate errors that can be fixed in the next iteration or two of the
     design.
     Non-persistent waiver classes provide information to other users who debug the same
     error database. For example, with an error defined as Error with the user comment, “this
     error needs to be fixed in conjunction with rule ABCD”, anyone reviewing the error in the
     same error database can see this guidance.

Creating a Waiver Database
     After you define all of the waivers for the current design, export the information to a
     standalone waiver database. The waiver database can either be in SQLite format

     comments, user-IDs, dates, waiver properties, and so on.




     You can export a waiver database using VUE or from the pydb_export command-line
     utility.
     To export a SQLite waiver database using VUE, select Classification > Export
     Classification Data (CPYDB).

Using a Waiver Database
     After you create the waiver database, you can use it as input to other IC Validator runs.
     The new runs do not have to be the same top cell. IC Validator imports all waiver shapes
     the Cell / Violation present in the current run. IC Validator waivers are fully hierarchical.




     The waiver_options() function provides control over how waivers are applied and
     reported during the IC Validator run. This command is divided into two main sections.
     The first section includes database management, where you provide the list of waiver
     databases and customize how each one is processed. The second section provides global
     waiver control that IC Validator uses for all waivers and reporting.
     The database management is controlled with the databases argument. IC Validator
     automatically detects the database format, and both CPYDB and OASIS formats can be
     supplied in the same IC Validator run. Layer mapping files are not required when using
     OASIS format waiver databases.
     For each waiver database, you can customize controls to provide flexibility across designs.
     This includes:
      • Control over what happens if the waiver database cannot be found.
      • If the errors waived with this database should be suppressed instead of
        classified. Suppressed means the waived errors are not written to the PYDB or
        LAYOUT_ERRORS file.

     Matching Modes
     You can control how IC Validator matches a waiver shape to a given error shape. All
     matching occurs after all interacting waiver shapes have been merged together and
     interacting error shapes have been merged together. In some situations, to allow the
     merging to occur, the shapes might need to be leveled to a common parent cell. The
     matching is done hierarchically, that is, the level-merged waiver shapes do not need to be
     in the same cell as the level-merged errors shapes to find a match.
     There are three matching modes available: EXACT, ENCLOSE (default) , and INTERACT.
      • EXACT mode specifies that the level-merged waiver shape must exactly match the
        level-merged error shape for the waiver to be applied.
      • ENCLOSE mode is the default matching mode. The waiver shape must enclose the
        error shape.
      • INTERACT mode specifies that any error which interacts hierarchically with a waiver
        shape is waived. Use the include_touch argument to allow outside-touch interactions
        to be considered as an interaction for waiving.
     Note:
         Use the tolerance argument to provide better matching with all-angle shapes.

     The matching mode you set in the waiver_options() function apply to all
     waiver_databases. You can override the matching mode for specific rules using the
     rule_overrides argument. For example, ENCLOSE mode is allowed for all rules except
     R.MY.STRICT_RULE. For that rule, waivers are applied only if the waiver and error
     shapes exactly match. For example,
     waiver_options(
       databases = { {"/path/to/waiver.oas"}},
       matching_mode = ENCLOSE,
       rule_overrides = {
         violation_comments = {"R.MY.STRICT_RULE"},
         matching_mode = EXACT,
         tolerance     = 0.005
       }
      );
