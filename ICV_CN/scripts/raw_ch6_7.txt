Introduction to IC Validator Explorer DRC



Introduction to IC Validator Explorer DRC
      Debugging DRC violations early in the design process can be complex and time
      consuming. For example, complicated DRC rules (multiple patterning and delta voltage)
      run for a very long time and do not add value when other simpler violations exist.
      A basic set of design checks can be used to debug typical early design issues: finding cell
      overlaps, improper fill, and routing issues does not require complicated rules. IC Validator
      Explorer DRC automatically determines these basic rules from the foundry runset. It also
      adds extra methodology rules and debugging capabilities. This results in a significant
      reduction in turnaround time.
      In addition, IC Validator Explorer DRC detects when design layers flag too many violations
      and deselects related slow-running rules. Such dynamic selection and execution of checks
      achieves a faster turnaround time than traditional full DRC runs.


Types of Explorer DRC Modes
      There are three Explorer DRC modes:
      • Explorer DRC Standalone Mode
         This mode runs automatically selected design rules from the foundry runset and
         IC Validator-added methodology checks.
         Use the standalone mode for designs with violations that require fast checking with
         low computing resources.
      • Explorer DRC Tiers Mode
         Explorer DRC tiers provide a systematic framework for executing and reporting the
         high-priority checks first. In the tiers mode, checks are completed regardless of
         performance. All rules are selected and executed based on the tier order and up to the
         specified tier.
         Performance is not the main consideration when you use this mode.
         Some tiers are reserved for Explorer priority rules and methodology checks. Most of
         the tiers however, are user-customizable. See Table 26 for more information.
         The tiers are executed in order of assigned priorities. Lower-numbered tiers have the
         highest priority. Undefined checks between Tier 0 and Tier 10 are executed after Tier
         10, as part of an “All remaining rules” tier. Results are updated during the run, as each
         tier finishes.

      • Explorer DRC Auto Mode
         Similar to the tiers mode, this mode also uses the Explorer DRC tiers. However, this
         mode also has the ability to stop slow-running rules.
         When design layers with violations are found in auto mode, related rules are stopped
         if their functions are slow-running. This allows for results from earlier tiers to be used
         to stop later functions/rules from running too long (rules from tier 0 and tier 1 are never
         stopped early).
         The performance of this mode depends on the number of DRC errors. The larger the
         number of DRC errors, the more likely it is that auto mode deselects rules and exits
         early to achieve a faster turnaround time.
         Use the auto mode when the number of violations in the design is unknown and you
         want to complete as many checks as possible. If the design is clean, auto mode does
         not stop any of the checks, and it produces full signoff results.

         TierNumber.

         are:

            default in Tier 0.
          ◦ EXPLORER.VOLTAGE. Disables voltage-based diagnostics that are included by

     Explorer DRC Results File
     Explorer DRC creates the RESULTS file, cell.RESULTS. This file provides results from the
     run and also the IC Validator command-line option used for the run.
     The RESULTS file is used as the starting point for analyzing the results of an Explorer
     DRC run. The Results summary section reports the DRC error statistics, as categorized in
     Table 28. Statistics include the total number of rules and violations in the different Explorer
     categories.


     Explorer DRC Errors File
     Explorer DRC creates a LAYOUT_ERRORS file, which provides layout errors that are
     flagged during the run. These errors are categorized in Table 28.
     To ensure the error report is concise, error coordinate information is suppressed
     in the LAYOUT_ERRORS file. This is equivalent to running error_options
     (report_error_details = false). The information is stored in the error database
     (PYDB), but only the violation summary section is written to the LAYOUT_ERRORS file.
     The LAYOUT_ERRORS file is generated after each tier/category so that you can
     reference it during the Explorer DRC run. The icv.log file indicates when a tier/category is
     completed, as follows:
     ICV_Engine run is 5% complete. Elapsed Time=0:07:24
     All Priority Rules are finished! 19103703 violations were found.

     Note:
         While storing error markers in the error database (PYDB), Tier 0 and Tier 1
         (Explorer priority checks and user-defined priority checks) enforce the limit
         set by the error_sampling_per_check argument (the default is 1 million).
         The limit of other tiers is based on the runset. See the IC Validator Reference
         Manual for more information about the error_sampling_per_check argument.

Debugging With Explorer DRC
     To analyze an Explorer DRC run,
      1. Run IC Validator with Explorer DRC.
      2. Review the RESULTS file.
          ◦ If the results are clean, go to signoff DRC. If the results are not clean, go to step 3.
      3. Load the Explorer DRC .vue file into VUE. Attach the layout editor to VUE.
      4. Click the Heat Map tab to start debugging. The Error Heat Map is a graphical interface
         used to visualize error distributions.
         Heat Maps are automatically enabled for Explorer DRC. See the
         “Introduction to the IC Validator Error Heat Map” chapter in the
         IC Validator VUE User Guide for more information.
      5. Similar to the RESULTS and LAYOUT_ERRORS files, the Explorer DRC errors
         are categorized by default in Table 28. In general, start debugging in order from
         methodology warnings, diagnostics, predefined priority rules, user-defined tiers and,
         finally, to all remaining rules.
         In addition, you can select the Clustered Errors category mode from the
         menu in the Violation Category window. In this mode, identical errors are
         clustered together so that multiple rules can be debugged at one time.
         See the “Introduction to the IC Validator Error Heat Map” chapter in the
         IC Validator VUE User Guide for more information on clustered errors.
      6. After rules are selected from their respective categories, isolate the areas with a high
         number of error counts (red regions in the heat map) and zoom into these dense
         regions.
      7. Probe the heat map and layout errors in these regions to analyze the underlying cause
         for the high error count. Probing might include:
          ◦ Zooming into regions
          ◦ Highlighting error markers in those regions
          ◦ Selecting or deselecting specific rules
      8. Repeat steps 6 and 7 until all categories/clusters are exhausted.

Introduction to IC Validator Explorer LVS
     Finding the root cause of LVS errors early in signoff LVS is critical in reducing the overall
     signoff period and meeting a tapeout schedule. Explorer LVS targets the System-On-Chip
     (SOC) full chip, and provides a solution where you can find the root cause of LVS issues
     with a quick turnaround time and efficient machine resources. This reduces the overall
     signoff time and effort.
     Explorer LVS focuses initially on LVS issues that stem from SOC integration, and then
     gradually expands its analysis to cover other potential LVS issues, such as LVS errors
     from the device or base layers or cells in the lower hierarchy.
     To check the issues from SOC integration, by default, Explorer LVS performs a text-based
     short check with only the equivalence cells and metal layers that make up the SOC Top
     (for example, P&R, PowerGrid, placeholder polygon fill cells that build up the main SOC
     structure, as opposed to macros and IPs that are instantiated underneath the main SOC
     structure, and so on). The scope of checking LVS issues can be expanded as needed
     using flexible options provided by Explorer LVS.
     Explorer LVS helps increase the productivity and efficiency of signoff LVS. It does not
     replace the traditional LVS tool. Final signoff LVS must run with the traditional LVS tool.
